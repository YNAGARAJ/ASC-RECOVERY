# Audit 03 — Money Correctness

Wave 1, Agent 3. Read-only audit of every money-handling path against CLAUDE.md
rules 2 (Decimal, ROUND_HALF_UP, 2 places) and 3 (no LLM computes/restates a
dollar amount), plus sign/double-count/idempotency/precision review.

Scope read: `src/domain/money.py`, `domain/contract.py`, `domain/variance.py`,
`domain/x835.py`, `ingestion/reconcile.py`, `ingestion/plan.py`,

`packets/prompt.py`, `packets/drafter.py`, `observability/metrics.py`.

## Findings

### [CRITICAL] Reversal netting silently fails to net (and can mis-link) when the reversal claim's line layout differs from the original
- **File:** src/ingestion/plan.py:86-100 (`_reverse_finding`) together with src/ingestion/apply.py:136-159 (`_apply_claim`)
- **What breaks:** A reversal (CLP02=22) is supposed to net a prior finding to exactly zero. `_reverse_finding` builds the reversing `Finding` with `line_index=prior.line_index` and `shortfall=-prior.shortfall`. The arithmetic itself nets exactly (Decimal negation is exact). But persistence keys off the *reversal claim's own* service lines: `apply._apply_claim` builds `service_line_ids` by enumerating `claim.service_lines` (0..k of the reversal claim), then `persistable = tuple(f for f in claim_plan.findings if f.line_index in service_line_ids)` (apply.py:139). If the reversal claim reports fewer lines than the original (common — payers frequently send a reversal with a collapsed/1-line body), the reversing finding for a higher `line_index` is **dropped**. The original `+shortfall` row stays on the books with no offsetting `-shortfall`, so the claim's reported recoverable dollars are overstated by the full original shortfall — a wrong dollar amount for a real claim. When the index *does* exist but the reversal claim's procedure at that index differs, `save_findings` (db/repository.py:511-525) attaches the reversing row to `service_line_ids[finding.line_index]` — i.e. to whatever procedure occupies that slot in the reversal claim — producing a finding whose `service_line_id` points at a different procedure than its own `procedure_code`/evidence text.
- **Reproduce:** Ingest an original 835 whose claim `PCCN=ABC` has 3 priced service lines, line index 2 underpaid (finding shortfall $80.00). Then ingest a reversal 835 with `CLP02=22`, same `PCCN=ABC`, carrying only 1 service line (index 0). `list_findings_by_payer_claim_control_number` returns the prior finding at line_index 2; `_reverse_finding` emits a reversing finding at line_index 2; `apply` drops it because `2 not in {0}`. `SELECT sum(shortfall) FROM findings WHERE payer_claim_control_number='ABC'` returns $80.00, not $0.00.
- **Fix:** Do not key reversal-finding persistence on the reversal claim's line positions. Either (a) match the reversing finding back to the *original* claim's service line (resolve by original claim_id/line_index, which requires carrying the original service_line_id on `PriorFinding`), or (b) persist reversing findings without requiring a matching reversal-claim line (allow `service_line_id` to reference the original line), and never silently drop a reversing finding — a dropped reversal must fail loudly or quarantine, since it corrupts recovery totals. Add a test asserting `sum(shortfall)==0` after original+reversal when the reversal has fewer lines.
- **Effort:** M

### [HIGH] Currency validator cannot catch a hallucinated whole-dollar figure written without a `$` and without cents
- **File:** src/packets/currency.py:23-37 (`_CURRENCY_PATTERN` / `extract_currency_figures`), used by src/packets/service.py:60-85
- **What breaks:** The regex only treats a number as currency if it is `$`-prefixed OR carries an exact 2-decimal suffix. A bare integer with neither — e.g. the LLM writing "the plan underpaid this claim by 5000" or "we are owed 1,234" — is never extracted. That means it passes *both* gates: the raw-draft reject (service.py:60, "raw currency figure") does not fire, and the post-substitution `validate_currency` (service.py:74) does not fire. A fabricated/restated dollar amount then ships inside an approved appeal letter to the payer, directly violating CLAUDE.md rule 3 ("no LLM ever restates a dollar amount"). The validator is the designed backstop for a misbehaving model, and it has a definite hole for the most natural way a model writes money in prose (round numbers, no symbol).
- **Reproduce:** `from packets.currency import validate_currency; validate_currency("We are owed 5000 for this claim.", frozenset())` → `CurrencyValidationResult(valid=True, unmatched=())`. A draft containing "5000" passes even though 5000 is in no allowed set.
- **Fix:** Extend detection to catch bare integers in monetary context, or (stronger) invert the strategy: after substitution, assert the final text contains *only* figures that are byte-identical to the injected placeholder strings, and reject any digit-run of length ≥ some threshold that is not one of those exact strings. At minimum, reject drafts whose raw form contains any multi-digit integer not equal to a known procedure/date token. Add a negative test with a no-`$`, no-cents hallucinated figure.
- **Effort:** M

### [HIGH] Set-membership validation accepts a real figure placed against the wrong label (wrong-token substitution)
- **File:** src/packets/service.py:40-49 and 73-85; src/packets/prompt.py:52-85 (`render_final_text`)
- **What breaks:** `_allowed_amounts` is a 3-element set `{expected_allowed, actual_allowed, shortfall}`. `validate_currency` only checks that each extracted figure is a *member* of that set — it has no notion of which figure belongs in which sentence. Substitution is by token, so if the LLM emits `{{EXPECTED_ALLOWED}}` in the sentence describing the shortfall (a plausible model error), the final letter states the shortfall as the expected-allowed dollar value. Every figure is still "real" (in the set), so validation passes and the letter is approved — but it misstates the dollar shortfall to the payer in a legal appeal document. This is precisely the "figure that coincidentally matches a real value but for the wrong line" case the validator was supposed to defend against; membership testing structurally cannot catch it.
- **Reproduce:** With expected=$150.00, actual=$100.00, shortfall=$50.00, script a drafter whose output uses `{{EXPECTED_ALLOWED}}` where the shortfall belongs. `generate_packet_draft` returns `success=True` with a letter claiming a $150.00 shortfall.
- **Fix:** Validate position, not just membership. Since figures are injected deterministically, do not let the LLM choose token placement at all: have the LLM emit a single neutral marker per slot and render each slot from a fixed sentence template, or post-validate that each labelled figure in the rendered text equals the specific value for that label (parse the known surrounding phrasing). At minimum, document this as an accepted limitation and require human review of figure placement before send.
- **Effort:** M

### [MEDIUM] BPR reconciliation adds PLB with no sign normalization; a standard positive-withhold PLB would false-flag or mask a mismatch
- **File:** src/ingestion/reconcile.py:28-42 (`reconcile_bpr`); parser at src/domain/x835.py:242-260 (`_parse_plb`) reads `Money(amount_str)` with the raw sign
- **What breaks:** `computed_total = claims_total + plb_total`, and the fixture/tests assume a takeback arrives as a *negative* PLB amount (tests/ingestion/test_reconcile.py:15,39 — "PLB -10.00"). In real X12 835, provider-level adjustments such as withholds (WO) and forwarding balances (FB) are frequently reported as **positive** amounts that *reduce* the check, with BPR02 = Σ(claim payments) − Σ(PLB). Against such a file, `claims + plb` diverges from BPR by 2×PLB, so a perfectly consistent remittance is flagged as a mismatch — or, if a genuine discrepancy exists that happens to offset, a real payer error is masked. The reconciliation only *flags* (it does not write a wrong figure into a finding), which caps the blast radius, but the sign convention is unvalidated and untested against the positive-amount case that real payers actually send.
- **Reproduce:** Build an 835 with claim total_paid 430.00, a withhold PLB of `+10.00`, and BPR02 = 420.00 (real-world encoding). `reconcile_bpr` computes 440.00 and reports `matches=False, difference=-20.00`, flagging a clean file.
- **Fix:** Normalize PLB sign at the parser or reconciler per X12 semantics (a positive PLB reduces payment): `computed_total = claims_total - plb_total`, or negate PLB amounts on parse. Add a reconciliation test using positive WO/FB PLB amounts, not only the negative fixture.
- **Effort:** S

### [MEDIUM] Idempotency protects only byte-identical files; a near-duplicate resend double-counts claims and recovery dollars
- **File:** src/db/repository.py:348-386 (`record_remittance_if_new`) and src/ingestion/pipeline.py:125-131
- **What breaks:** Dedup is by `sha256(content)` against the `(tenant_id, file_hash)` unique constraint (db/models.py:157-159), and `_ingest_file_impl` correctly short-circuits to `DuplicateOutcome` on `is_new is False`, creating no claims or findings. So re-ingesting the **exact same bytes** twice is genuinely idempotent — verified against the real dedup path, not the test docstring. However there is no dedup at the claim level: `claims` has no unique constraint on `(tenant_id, payer_claim_control_number)`. A payer resend that differs by even one byte (added whitespace, re-wrapped segment terminator, trivial ISA control-number change) hashes differently, passes dedup, and inserts a second full set of claims and findings for the same `PCCN` — doubling `dollars_detected` and the recoverable total for those claims. Payer resends of the same remittance with cosmetic differences are common in practice.
- **Reproduce:** Ingest an 835. Ingest the same logical file with one trailing newline added. Two `remittances` rows, two sets of `claims`/`findings` for the same PCCNs; `sum(shortfall)` doubles.
- **Fix:** Either add a uniqueness/upsert guard on `(tenant_id, payer_claim_control_number)` (with an explicit correction/replacement path for legitimate corrected remittances), or canonicalize the file (normalize whitespace/terminators) before hashing. Document the chosen resend semantics.
- **Effort:** M

### [LOW] LLM cost estimate quantizes with banker's rounding (ROUND_HALF_EVEN), not ROUND_HALF_UP
- **File:** src/packets/drafter.py:40 (`estimate_cost` → `cost.quantize(Decimal("0.0001"))`)
- **What breaks:** This uses the default Decimal context rounding (ROUND_HALF_EVEN), the exact class of default-rounding leak rule 2 warns about. It is not claim/patient money — it is a non-authoritative LLM cost estimate feeding telemetry — so the impact is negligible, but it is the one quantize in the codebase for a dollar-denominated value that does not use ROUND_HALF_UP, and it will read as a rule-2 exception during review.
- **Reproduce:** `estimate_cost` inputs producing a 5th-decimal `...5` half will round to even, not up.
- **Fix:** Pass `rounding=ROUND_HALF_UP` explicitly, or route the value through a dedicated non-money helper and note it is telemetry-only.
- **Effort:** S

### [LOW] UNPRICED findings generate appeal packets asserting $0.00 expected and $0.00 shortfall
- **File:** src/api/repository.py:675-683 (`generate_packet` PromptInput) with src/domain/variance.py:112-131 (UNPRICED finding has `expected_allowed=None`, `shortfall=Money.zero()`)
- **What breaks:** For an UNPRICED_CODE finding, `expected_allowed` is coerced to `"0.00"` and `shortfall` is `"0.00"`. No money is misstated (both really are zero/unknown), but the endpoint will happily draft an appeal letter claiming a $0.00 expected amount and $0.00 shortfall — a coherent-looking but meaningless demand. Not a money error; a correctness/UX gap.
- **Reproduce:** Create a finding with `root_cause=UNPRICED_CODE`, call `generate_packet` for it; the rendered draft substitutes 0.00 for expected and shortfall.
- **Fix:** Refuse packet generation for UNPRICED_CODE (and any zero-shortfall) findings, or surface "unpriced — no contracted amount on file" rather than $0.00.
- **Effort:** S

## Categories confirmed clean (with evidence)

**`float` in any money path — CLEAN.** Grepped `float|quantize|ROUND_|float\(` across all of `src/`. Every hit is one of: (a) `domain/money.py`'s own type-rejection guard (`Money`/`Rate` raise `TypeError` on `float` and `bool`, money.py:14-20); (b) `security/rate_limit.py` token-bucket timing (not money); (c) `observability/alerts.py` recall/precision *rates* (not money); (d) `observability/metrics.py:115,122`, the single deliberate, documented telemetry-only `float(dollars_detected)` / `float(cost_usd)` conversion at the OTel boundary (metrics.py:18-24), which only ever *receives* an already-computed Decimal and never feeds a value back into the system of record. No money-bearing DB column is float: every currency column in `db/models.py` is `Numeric(12, 2)` (fee_schedule_lines.allowed_amount:152; claims total_charge/total_paid_reported/patient_responsibility:194-196; service_lines charge/allowed/paid_computed:230-232; adjustments.amount:254; findings expected_allowed/actual_allowed/shortfall/amount_recovered:277-290), matching Money's 2-place guarantee. `percent_of_charge_rate` is `Numeric(9,6)` (models.py:123) — correctly a Rate, not currency, and read back as `Rate(Decimal)` (repository.py:174).

**ROUND_HALF_UP consistency — CLEAN for claim money.** The only quantization of currency is `Money.__init__` (money.py:66-69), which always applies `quantize(TWO_PLACES, rounding=ROUND_HALF_UP)`. Every `Money` arithmetic op (`__add__`, `__sub__`, `__neg__`, `__abs__`, `times`, `allocate`) returns a fresh `Money`, so results are always re-quantized HALF_UP; no banker's-rounding can leak into a claim figure. `Money.times` computes `self._amount * rate.as_decimal()` (exact Decimal product) before quantizing, so the rate's extra precision is preserved until the single HALF_UP step. The only non-HALF_UP quantize anywhere is the LLM cost estimate (LOW finding above), which is not claim money.

**Sign / subtraction order — CLEAN.** `variance.evaluate_claim` uses `shortfall = expected_allowed - actual_allowed` (variance.py:134): underpaid ⇒ expected > actual ⇒ positive shortfall. `reconcile_bpr` uses `bpr_total_paid - computed_total` (reconcile.py:36). `x835._finalize_line` derives `allowed = charge - CO_total` then `paid_computed = allowed - PR_total` (x835.py:271-272), the standard 835 derivation. Reversal negates via `-prior.shortfall` (plan.py:94). All directions are correct. (The PLB *sign convention* concern is the separate MEDIUM finding, and is a semantic-encoding issue, not a subtraction-order bug.)

**Money.allocate residual — CLEAN.** `allocate` (money.py:111-120) uses integer-cent largest-remainder: `total_cents = int(self._amount * 100)` (exact, since `_amount` is already 2-place), `divmod(total_cents, parts)`, distributing the remainder one cent at a time. `sum(result) == self` holds exactly, including for negatives (Python `divmod` floors, remainder is non-negative, so the shares still sum to the original). The case-rate allocation in `contract.price_claim` (contract.py:229-233) relies on this and therefore leaves no rounding residual — the flat rate is split exactly across eligible lines. (Whether case-rate *overwrites* previously-priced/UNPRICED lines is a pricing-semantics question for Agent 4, not a rounding residual.)

**JSON / API-boundary precision — CLEAN.** Every money field on the API models is `str`, never a JSON number: `api/schemas.py` (FindingSummaryOut expected_allowed/actual_allowed/shortfall/amount_recovered:39-47; ServiceLineOut charge/allowed/paid_computed:86-88; AdjustmentOut.amount:95; RecordOutcomeIn.amount_recovered:144), and the backing dataclasses in `api/repository.py` carry the same `str`-typed money, produced via `str(Decimal)` (`_finding_to_summary`:407-414, `get_finding_detail`:512-525). Contract JSONB (de)serialization stores rates and `flat_rate` as decimal strings, not JSON numbers (repository.py:62-151), explicitly to avoid float re-parsing — verified round-trip via `Rate(str(...))` / `Money(str(...))`. `IngestionOutcome.dollars_detected` (a Decimal) is not exposed on `IngestionOutcomeOut` (schemas.py:147-152), so it cannot leak as a JSON number.

**Postgres column precision vs Money's 2-place guarantee — CLEAN.** All currency columns are `Numeric(12, 2)` (see float section). Scale 2 exactly matches Money; precision 12 allows up to ~$99,999,999.99 per value, adequate for a single ASC claim/line. Values written via `.as_decimal()` (already 2-place) and read back as Decimal into `Money(...)`; no truncation or widening at the boundary.

**Ingestion idempotency (byte-identical) — CLEAN.** `record_remittance_if_new` uses `pg_insert(...).on_conflict_do_nothing(index_elements=["tenant_id","file_hash"]).returning(id)` and returns `(row, is_new)` correctly for both the inserted and pre-existing case (repository.py:359-386); `_ingest_file_impl` returns `DuplicateOutcome` and writes nothing when `is_new is False` (pipeline.py:127-131). Re-ingesting identical bytes produces identical totals. The residual risk is cosmetic-resend near-duplicates (MEDIUM finding above), not the byte-identical path.

## Notes for the consolidation wave
- The CRITICAL reversal finding and the two HIGH LLM-boundary findings are the ones that can put a *wrong dollar figure* in front of a real payer; prioritize accordingly.
- The two LLM-boundary HIGHs share a root cause: `packets.currency` validates set-membership of loosely-detected figures rather than exact, position-bound equality of injected values. A single redesign (render each dollar slot from a fixed template and assert byte-exact injected strings) closes both.
